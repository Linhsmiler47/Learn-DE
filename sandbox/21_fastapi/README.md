# Phase 21 — Backend API with FastAPI

## Learning Objectives

- Build a backend API exposing analytics-ready data with FastAPI.
- Understand request/response models, Pydantic validation, and basic auth.
- Test and containerize the API.

## Prerequisites

- Phase 20 — completed Data Engineering project
- Phase 09 — Python

## Reference Materials (`ref roadmap/`, read-only)

- [EDAI-1 curriculum: WebAPI lesson (API architecture styles, auth, FastAPI fundamentals to optimization, request validation, healthcheck, Locust performance testing)](../../ref%20roadmap/EDAI/Engineering%20for%20Data%20&%20AI%20%28EDAI%20-%20K9%29%20%28Official%29%20-%20Start%20Date_%2001_04_2026.xlsx)

> EDAI teaches FastAPI early (as a general engineering skill before the DE layers). This path deliberately places it here instead, per the requirements document: build the DE pipeline first, then expose its output through an API. Both orderings are valid — this one matches your stated goal of learning DE fundamentals before building consumer-facing services.

## Core Concepts

- Backend architecture basics, API endpoint design
- FastAPI: path/query params, request and response models, Pydantic
- CRUD fundamentals, database connections from an API layer
- API documentation (OpenAPI/Swagger, auto-generated by FastAPI)
- Authentication fundamentals, logging, testing, Dockerizing FastAPI

## Exercises

- Build a FastAPI service exposing the analytics-ready marts from Phase 20's project as read-only endpoints.
- Add Pydantic response models and validate query parameters (pagination, filters).
- Add a basic auth mechanism (API key or JWT) protecting write/sensitive endpoints.
- Write tests for the endpoints and Dockerize the service (reusing Phase 05 patterns).

## Expected Output

- A working, tested, Dockerized FastAPI service exposing real pipeline output.

## Validation Checklist

- [ ] OpenAPI docs (`/docs`) accurately reflect every endpoint's request/response shape.
- [ ] Unauthorized requests to protected endpoints are correctly rejected.

## Common Mistakes

- Exposing raw database errors to API clients instead of clean error responses.
- Skipping pagination on endpoints returning potentially large result sets.

## Optional Challenges

- Load-test the API (e.g., with Locust, as mentioned in the EDAI reference) and identify its first bottleneck.

## Reflection Questions

- What decisions from Phase 20's data model made this API easy or hard to build?
